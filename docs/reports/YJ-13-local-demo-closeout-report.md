## GATE-0 认证限流

YJ-12 的两次原始回执仍是 **22/22、18/22**。后一次有四组在验证码路由收到 429，历史记录没有当时的 IP 桶、计数或响应头。新测量可以解释旧失败机制，无法反向证明每一个旧响应的瞬时数据库状态。[YJ-12 原始回执](evidence/YJ-12/regression.json)

逐项核对九霄的 auth 路由、EmailAuthService 和 PostgresEmailAuthRepository。一个综合回归有多个宿主。createPlayers 使用新的 example.invalid 邮箱，有些用例为切换账号会显式登录第二人；代码映射由每个宿主持有。YJ-12 的 pg_ctl 独占解决了启停竞争，但这些宿主仍接到同一个持久 cards 认证库。重复运行会累积同源配额。旧记录未指向失控浏览器或自动重发验证码。

在全新集群，通过原 `POST /api/auth/code` 先对 60 个不同的合成邮箱各请求一次，再对第 61 个新地址请求一次。HTTP 连接来自回环，测试宿主的 fetch 转发未传 socket bindings，原认证路由以 `unidentified` 作为来源键。第 61 次实际取得 **429、RATE_LIMITED、Retry-After 60**。拒绝前后均为同一来源桶 60，单邮箱最大 1，全局 60，未达到全局每小时 600。源码顺序为先查来源，再查全局、邮箱发送间隔及单邮箱次数。因此在这个复现中确实命中了 per-IP 每小时 60；头部的 60 秒为路由统一提示。完整套件中直接挂载的其他宿主也出现了真实回环来源桶。[限流回执](evidence/YJ-13/limit-fixed.json)

新入口每轮 initdb，使用新的 SCRAM 凭据、原 SQL 迁移与应用角色授权，API 以 cards_demo_app 连接。没有写共享认证库或调整正式来源配额。每个测试组仍用独立投影库。最初沙箱拒绝回环连接，获本轮授权后重试。首次 22 项并发导致 PostgreSQL 拒绝连接（SQLSTATE 53300），8 项失败，认证请求同时出现 503。限制到两个并发宿主后为 21/22，一项在 14 路并发反馈中未取到预期 ID，该次未采集具体 HTTP 状态。为独立集群显式配置 100 个连接，与已初始化的上游本机演示库相同，补上反馈响应状态断言，保留原测试并发。测试时长阈值保持原值。[14/22 回执](evidence/YJ-13/suite-1.json) · [21/22 回执](evidence/YJ-13/bounded-1.json)
