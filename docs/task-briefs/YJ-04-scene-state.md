## 三、真实来源边界

普通角色卡当前接口为：

```text
GET /api/card-import/sessions/:id/history?after=<revision>
```

响应是裸数组；每行只有 key、action、narrative、resulting_revision。服务先检查 owner/session，再读取 completed 请求，按 resulting_revision 升序，最多 100 行。没有 hasMore、nextCursor、total，也没有每行 status。

owner 来自既有会话身份解析，不能信任任意客户端提交的 ownerId。fromCardHistory 只负责校验和投影，不负责鉴权。实际接入可使用现有服务内适配或已有受鉴权 HTTP 路径，选择后记录准确代码位置和权限边界，不建立第二套账号系统。

本轮先消费已验证的普通独立角色卡历史。原生权威回合、群聊历史及开场 greeting 不作为隐藏前置：

- greeting 在会话详情，初始修订为 0；不能把 0 改成 1 或造一个请求 key。
- 群聊的 group-history 结构不同，普通 history 中也可能存在群聊 JSON 正文；应识别本次支持的会话模式，不能误按普通叙事处理。
- 尚未支持的来源明确报未适配，不修改上游权威状态，不把范围选择写成用户永久放弃相关玩法。

上游参考：[host.ts](https://github.com/L-core-dev-team/Nine-cloud/blob/cd25360c7929e10f8b2b0fad342fedd943d4f323/apps/api/src/card-import/host.ts)、[router.ts](https://github.com/L-core-dev-team/Nine-cloud/blob/cd25360c7929e10f8b2b0fad342fedd943d4f323/apps/api/src/card-import/router.ts)、[service.ts](https://github.com/L-core-dev-team/Nine-cloud/blob/cd25360c7929e10f8b2b0fad342fedd943d4f323/apps/api/src/card-import/service.ts)。

## 四、稳定地点与状态模型

### 4.1 地点身份

角色卡地点归属按 kind + ownerId + sessionId + sceneId 表达。key/revision 记录建立或更新地点的事件，不进入稳定地点主键。UUID 先经过现有契约规范化，再用于关联和去重；不把其他不透明标识一律转小写。

别名是指向已知地点的关系，不是另一个新地点。至少证明：

- 同一家酒馆从“青石酒馆”改称“老周的店”，可在有明确依据时保留 sceneId。
- 不同村庄各有“青石酒馆”，不会仅凭同名合并。
- 人物谈及远山、回忆昨日或计划明日出城，当前地点仍保持不变。
- 地点识别有歧义时保留未定位/候选及理由，不随意创建或合并。

地点层级和关系按现有契约保存最少信息。地图布局、跨尺度拼图和完整地理坐标继续后置。

### 4.2 持续状态与本轮变化

currentFacts 只筛当前事件，不能替代世界状态恢复。加载上一份已保存状态，再应用本轮明确变化：

- 没提到某个人，不自动删除该人物。
- 已明确新增/离开的角色或变化应更新，不能被后续普通交谈抹掉。
- 图片偶然多出的门窗、光点或道具，不进入权威事实。
- 记录事实的来源与最后确认依据；最后已知状态不自动等于所有信息永远有效。
- 证据不足时保留不确定/待处理，必要时不输出当前画面计划，不虚填时间、地点或人物来满足 schema。

本轮应有可替换的“正文到场景变化”边界，并明确输入中的当前/回忆/计划/传闻及玩家可知范围。可以先用固定、显式标注的合成变化证明状态机；如用模型或其他提取器处理自由文本，必须另列真实效果和局限，不能把人工标签测试声称为 AI 已能理解任意剧情。没有获准真实文字模型，不阻塞读取与持久化工作。

### 4.3 视觉版本

普通交谈沿用原视觉版本。人物、地点特征、时间/灯光、视野或人称相关可见状态实质改变时，分配新的版本并保存前后关系。

同一个地点的同一版本只能对应同一份规范化可见事实。不同事件可以引用同一版本；不同图片也可表达同一状态。地点状态与“当前所在地点”分开保存，离开某处不等于删除该地点。

复访时读取持久化结果；在本批明确“状态未变”的样例中继续使用已有版本。不得依赖上次页面内存或完整聊天上下文才能恢复。角色数量为 3→5 的明确变化，重放后仍只能增加一次。

## 五、分页、重放与原子保存

### 5.1 消费检查点

以最后成功提交的修订作为 after。满 100 行时继续读取，直至完成当前有限批次；可采用受信高水位或有限轮询边界，避免在不断新增历史时无限执行。错误与未处理记录要可见。

不要看到一页就先把检查点写到页尾。中间某条失败、校验不通过或冲突时，不得把它当成功跳过。可保留待处理记录，但必须说明如何补处理、检查点如何推进以及如何避免漏掉事件。

### 5.2 去重与冲突

使用现有 eventKey 语义，记录来源修订和输入摘要：

- 同事件、同修订、同内容：幂等返回，不重复加人或新增视觉版本。
- 同事件不同修订/内容：记录冲突，不静默覆盖。
- 同一修订出现矛盾事件、历史倒退或缺口：明确处理，不用“最新一次返回”覆盖已提交状态。
- 记录原始正文与规范化正文的区别。fromCardHistory 会 trim 首尾空白；摘要采用哪种内容要写清，原始字节对账不能基于已 trim 的正文冒称完成。

requestKey 目前是规范化的逻辑内容字符串。若持久层使用派生摘要或索引键，保留与原逻辑内容的关联及冲突核对，不能仅为建索引静默改变公共契约。

### 5.3 状态与检查点一起提交

“已消费事件、场景/视觉变化、消费检查点”必须原子提交或具有等效的可证明恢复行为。两个读取者同时处理相同来源时，不能重复应用或由旧状态覆盖新状态。

优先复用 YJ-01 已跑通的 Node/PostgreSQL，在隔离开发环境中使用映界自己的存储范围。表名与最小实现由执行者核查后决定，不把这项建议自动升级为永久部署方案。

不要直接复用上游权威表保存映界状态，不修改上游回合结算。若确因环境限制采用其他持久化实现，明确目标数据库未验证，仍要证明锁/原子写入、重启恢复和冲突处理。只存在内存、只 dump 一份 JSON 却不处理写入中断，不能算本轮持久化完成。

映界处理失败应保留可重试状态，不能回滚或阻塞上游已经完成的文字回合。取消当前呈现、切换会话/账户后，迟到读取不能成为另一个当前会话的状态；删除或撤权也不能通过旧缓存恢复访问。

## 八、需要证明的代表性检查

| 检查 | 期望证据 |
| --- | --- |
| 原契约与补丁 | 全部原有测试加新增两组通过；不新生图 |
| 来源与鉴权 | 已完成历史正常读入；错误用户/会话、未完成请求和不支持模式不能被误认为受信当前来源 |

| 同页重读与进程重启 | 已消费事件不重复应用，最后成功检查点可恢复 |
| 提交中断 | 在写状态/写检查点边界故障后，重新读取不会丢事件或重复变化 |
| 并发/过期写入 | 两个消费者竞争同一事件或旧快照写入时，状态不会倒退或重复加人 |
| 酒馆变化 | 三人、普通交谈、五人、离开、明确无变化复访、傍晚；状态和版本变化符合事实 |
| 名称与范围 | 有依据的改名不换地点；同名异地不合并；每轮 key/revision 不改变稳定地点主键 |
| 未提及与非当前内容 | 普通对话不删除已有角色；回忆/计划/传闻不搬迁当前地点 |
| 矛盾与未知 | 同 key 不同内容、缺口、未知地点或不可确定当前事实，有明确结果与补处理路径 |
| 退出与撤权 | 切换账户/会话、删除或失去访问权后，旧缓存与迟到响应不能恢复当前访问 |
