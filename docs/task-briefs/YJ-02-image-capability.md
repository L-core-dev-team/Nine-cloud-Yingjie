优先使用已具备且有有效授权的图片服务做最小实验。若暂缺真实服务，先完成样例、能力核查、调用记录设计和可离线检查的部分，准确记录真实调用缺口；不能把模拟返回值、占位图或手工示意图当作真实API验证通过。

## 二、这一步必须回答的问题

1. 当前可用的程序接口能否生成初图，并实际接收参考图片进行后续生成或编辑？
2. 增加人物时，能否保留同一酒馆的主要结构与原有人物，而不是重新生成一个相似主题的酒馆？
3. 玩家离开后回来，是否能够恢复同一场景及已发生变化？普通回合没有视觉变化时能否直接复用已接受图片？
4. 模型失误时，哪些错误能够直接看出，哪些无法确定，应该怎样降级？
5. 实际请求、结果图片、参考关系、耗时、失败和可获得的费用信息能否追溯？

必须分别记录“能力有无”“本批样例效果”“是否适合继续接入”。样例成功不能证明任意剧情稳定；模型表现不佳也不能被美化成通过。

## 三、已验证输入与尚缺条件

### 已有基础

YJ-01已验证同一独立角色卡会话的两次行动、刷新恢复和数据库对账。可利用的归属为owner、session、request key和revision。当前角色卡路径没有原生saveId、branchId，不应为填表而虚构这些身份。

候选接入方式是在既有鉴权边界内读取已完成历史，相关接口为GET /api/card-import/sessions/:id/history?after=<revision>。owner来自既有身份解析，不能信任任意客户端提交的owner值。来源回合与后续视觉版本应分开理解；普通回合推进不意味着必须重画。

本阶段可以单独运行图片能力实验，不必先把历史读取适配器完整接入页面。若使用手工场景样例，应标为synthetic-fixture；若读取实际会话历史，应记录真实来源，不能把两者混写。

### 真实调用条件

执行前记录实际服务、模型、程序入口、官方能力说明、参考图输入方式及当前允许的调用范围。只记录配置名称和是否可用，不输出密钥。

- 已有可用且获准的服务：在既有授权和额度范围内执行。
- 仅支持文生图，不支持参考图：明确记为参考图能力缺失，不把重复文本描述冒充参考图编辑。
- 只有聊天界面的手工出图：可记录为人工效果样例，不能写成程序API已接通。
- 缺少服务或有效调用条件：先完成不依赖真实调用的工作，并将真实图片部分标为BLOCKED或NOT_RUN。

具体供应商、永久模型、图片规格、正式预算和密钥保存产品方案仍未冻结。实验临时参数写明用途；不重新发起费用、多人、素材准备或密钥保存的大轮访谈。

## 四、最小酒馆剧情样例

以下内容专用于能力验证，是合成测试样例，不属于已确认的九霄世界书，也不是YJ-01固定回复中已经发生的剧情。可调整名称和描述以适应模型，但应固定一次实验使用的版本，不能看到图片后再修改期望掩盖失败。

### 稳定地点与观察范围

- 实验地点编号：fixture-tavern-01，仅在测试样例内使用。
- 室内木梁大厅；画面右侧为长柜台，左侧有两扇窗，中间有三张方桌。
- 初次使用固定的室内广角观察位置，优先让主要结构与在场人物可辨认。
- 初代图片比例和像素仍未决定；一次对照实验中保持同一组可用参数。
- 不要求小道具达到像素级一致；检查主要结构、人物状态和明显剧情冲突。

### 分段剧情

| 阶段 | 明确的剧情事实 | 画面目标 |
| --- | --- | --- |
| S0 初次进入 | 酒馆中有一名掌柜、两名客人，共3人；掌柜位于柜台后，两位客人衣着可区分 | 建立初图I0，保存稳定特征与可见人物 |
| S1 普通交谈 | 玩家与掌柜谈起远处的山峰，现场人物和环境没有变化 | 当前地点仍是酒馆；复用已接受的图片，不因为提到山峰而换景 |
| S2 人物到场 | 玩家救回的两名旅人已经进入酒馆；原3人仍在，总共5人 | 使用I0作为参考生成I1，保留主要结构和原有人物，加入两名可区分的旅人 |
| S3A 离开后复访 | 玩家短暂离开，再回来时仍是同一酒馆，5人均未离开，环境没有新增视觉变化 | 从实验记录恢复I1并复用；不必额外调用图片模型 |
| S3B 复访后的明确变化 | 剧情进一步明确天色转晚、灯已点亮，其余主要结构和5人在场事实不变 | 在I1合格的前提下以I1为参考生成I2，检查新变化没有抹掉已发生的人物变化 |

如果初图或更新图不符合要求，标记实际错误，保留失败输出。未被接受的图片不能无说明地成为下一阶段“正确参考”。需要修正时，在现有调用范围内调整一个主要因素，并记录新的尝试和参考关系。

S3B用于检查连续两次参考更新。若服务条件或额度无法覆盖，应明确标记未执行，不用S3A的旧图复用替代该能力结论。

## 五、执行步骤

### 步骤1：核查服务与固定实验条件

依据真实接口说明和可用配置确认文生图、参考图更新、同步/异步返回、任务查询和图片下载方式。记录实际支持项；不为了本次实验接入多家供应商或安装大型工作流平台。

固定一个候选服务、一组图片参数和一版剧情样例。只保留必要的临时选择，避免在多模型、多画风、多尺寸之间同时切换，导致无法判断变化原因。

### 步骤2：准备样例与最小调用入口

建立能被复跑的实验输入和最小调用方式。可以是单个脚本、已有工具入口或现有适配器的实验封装；本任务不规定正式模块、数据库表、队列和UI结构。

区分：

- 直接写好的场景输入：验证图片模型及参考图能力。
- 从剧情样例提取场景再调用：额外验证所采用的提取方法。
- 从九霄真实会话历史到图片：属于进一步集成证据；只有实际执行才记录通过。

不要把第一层效果写成第三层已经完成。

### 步骤3：运行初图、到场更新和后续参考更新

按S0、S2、S3B形成I0→I1→I2的来源链，记录每次实际发送的文本、参考图片文件及其摘要、模型参数、返回结果和人工观察。

S1和S3A通过实验状态与记录检查复用，不为没有视觉变化的阶段额外生图。不得只重新发送相同文本、完全不发送参考图，却声称参考更新已验证。

保留所有实际尝试，包括失败、拒绝、取消和不合格图片。需要针对明确问题复测时才追加尝试；不只挑最好的一组展示，也不为了凑测试数量持续调用。

### 步骤4：检查错误和恢复边界

实验入口至少能够报告没有服务、明确失败、拒绝、超时或结果未知。已有请求标识时先按服务能力查询原任务；没有查询能力时记录限制，不无依据重复付费生成。

可使用明确标注的离线故障样例检查错误记录，不必为了覆盖失败而故意产生额外付费请求。实验脚本处理错误通过，不等于完整映界文字不阻塞和迟到防覆盖已经实现；后者仍由YJ-05、YJ-08验证。

### 步骤5：得出能力结论并给YJ-03交接

说明支持什么、失败在哪里、目前适合哪种使用方式，以及下一步需要哪些字段或能力。若无法稳定保留酒馆主要结构和已确认人物变化，明确提出局限与保守降级，不承诺“零穿帮”。

YJ-03可以提前整理不依赖供应商能力的资料，但依赖参考图、查询和存储能力的正式契约，应等待本阶段实际证据；不要在真实图片部分阻塞时把全部接口写成已验证定案。

## 六、图片审阅方式

| 观察项 | 需要记录的事实 |
| --- | --- |
| 地点身份 | 柜台、窗户、桌子、主要木梁关系是否仍支持辨认为同一酒馆；改变视角不能只按屏幕坐标比较 |
| 人物变化 | 初始3人和到场后5人是否可辨认；新增、缺失、重复或遮挡分别记录 |
| 连续变化 | I2是否保留I1已新增的人物，是否出现回退到初始人数 |
| 已知事实 | 是否画出剧情没有确认的人物、外部地点、未来事件或隐藏内容 |
| 画面适用性 | 普通交谈和无变化复访是否仍可使用已接受图片 |
| 参考关系 | 请求实际使用了哪张参考，输出是否确实与其关联 |
| 可判断程度 | 明确符合、明确不符、无法判断分别记录；看不清不能算通过 |

人工观察需写具体位置或现象。若使用视觉模型辅助审阅，也要标记方法与局限。图片哈希只能用于识别文件，不能证明语义连续性；固定seed也不能被当作一致性保证。

不在本任务冻结产品评分阈值、合格率或最低画质。报告实际样本数、失败数和观察到的限制即可；小样本不外推稳定成功率。

## 七、需要保存的实验信息

建议记录以下信息，作为YJ-03的输入；此清单不是最终数据库方案：

- 实验批次、样例版本、场景阶段和输入来源类型。
- 使用真实历史时的owner、session、request、revision；纯fixture不要伪造生产归属。
- 模型、接口能力、实验临时参数和实际请求时间。
- 实际提示内容、参考图标识、参考图片文件及其内容摘要。
- 服务提供的请求/任务标识、结果状态和查询过程。
- 原始结果图片、文件摘要、后续使用的参考关系。
- 可观察的请求耗时、下载时间、调用次数和服务返回的用量。
- 实际费用、估算值或未知的区别；没有数据时写未知，不当作免费。
- 人工审阅结果、失败原因、纠正尝试和下一步建议。

图片应保存为可复查的文件，不能只留下可能过期的链接。使用实际获准的存储位置并提供可访问路径。避免把临时授权URL、密钥和私人会话正文写入公共日志。图片批量入库、正式对象存储和许可证决定另按项目规则处理。

## 八、交付物与完成判定

建议输出：

1. docs/reports/YJ-02-image-capability-report.md：条件、方法、每个阶段的结果、图片对照、限制及建议。
2. docs/reports/evidence/YJ-02-image-runs.json：去除敏感信息的实际调用和审阅记录。
3. 可复跑的最小入口及明确标注的剧情样例。
4. I0、I1、I2及所有失败尝试的可访问文件，附参考关系。
5. 给YJ-03的能力清单：参考图数量和方式、编辑能力、任务查询、结果保存、错误分类及未验证项。
6. 更新任务状态、验证记录、交接说明；产品决定仍保留原等级。

上述路径是待产出建议，不表示文件已经存在。

完成层次应明确：

- 只做好样例、脚本或模拟结果：准备工作完成，真实图片部分仍待执行或阻塞。
- 已执行真实API实验：可完成本轮能力评估，逐项写PASS、FAIL、BLOCKED或NOT_RUN，不能把效果失败改写成成功。
- 核心连续性有可复查样例：可以据此推进相应的YJ-03契约设计，但仍不是最终产品验收或长期稳定性保证。
- 核心参考更新不具备或效果无法支撑目标：提交明确负面结论和下一步局部调整；依赖该能力的实现保持受阻，不先堆完整界面。
