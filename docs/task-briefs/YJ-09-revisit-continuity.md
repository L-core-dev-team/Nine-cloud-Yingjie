## 二、必须明确保留的事实边界

### 2.1 已确认世界状态与当前展示资格分开

YJ-08 的 `zh-visible-clause/1` 能识别少量明确句式。当前 `project` 在接到 `unknown` 时把当前位置标记为 null，同时保留已有地点记录。YJ-09 须明确以下三种情况的区别，必要时以最小改动补充可验证的未就绪原因：

- **明确离开当前地点**：人物仍可以存在于被离开的酒馆，但玩家当前不在那里；旧酒馆画面不是当前显示对象。
- **仍在当前地点，但存在未解析的可见变化**：例如“众人告辞，只剩掌柜独自守店”。可以保留最后已确认世界事实及来源，必须阻止旧五人图被当成当前一人图；不应以“当前位置必然改变”混淆语义，也不能据此把所有人判为确实离开。
- **无变化的对话、回忆、传闻、计划或引语**：没有当前变化证据时继续使用符合当前视觉版本的图片；引语中的“某人离开”不是已经发生的离场事实。

如现有数据契约不足以同时表达“地点已知、视觉事实待核实”，可以在 YJ-09 内部状态/审计中增加最小标志与恢复路径，**不未经协调擅自更改公共 Schema**。位置与可见事实的版本、资格、事件来源必须保持一致。

### 2.2 谨慎理解离场、复访和称谓

- 不提某个人不代表他离开；“他出去了”“后来走了两人”等缺少指代或范围时，不能胡乱决定从哪个已知人物集合删除。
- 明确的“只剩掌柜”可作为**需要校验的全量在场人物重述**候选；必须确认是当前、亲眼可知而非别人的说法、梦境或未来计划。名单更新可能触发新视觉版本。
- 连续两个入场/离场事件要按已保存正文顺序消费。重复处理相同事件不应重复增减人物，同一已知成员反复出现但事实未变不应凭空产生新视觉版本。
- 地点改名、昵称、别名不会单独改变 `sceneId`；“东村青石酒馆”和“西村青石酒馆”仅同名时不可合并。明确复访同一已知地点才能继承历史状态；有疑义时先未就绪。
- 图片中的偶然人物、道具和世界书中提到的秘密或未来事件不能反向写入当前故事事实。

## 三、提取器改进与语料对照

当前已核对的额外散文集 7 段中 4 段与同一开发会话预先写的标签一致，另 3 段保守放弃判断。这只是合成基准，并非真实玩家正确率。

优先针对三段已记录缺口做**定向且可验证**改进，避免直接用更宽泛的正则吃掉否定或引语：

| YJ-08 尚未处理的合成正文 | 对照语义目标 | 必须注意的反例 |
| --- | --- | --- |
| “刚还在柜台边的紫衣客推门出去了，厅里又安静下来。” | 在当前已知名单中移除明确指定的紫衣客；保留其余成员 | “听说紫衣客推门出去了”、计划出去、指向别处、人物身份无法确认 |
| “堂里的人纷纷起身告辞。门一合，只剩掌柜独自守店。” | 当前视野中只剩掌柜，具备足够证据时按全量可见名单覆盖 | 引用别人的描述、“仿佛只剩”、未确认地点、从历史回忆到当前的混用 |
| “窗纸上的日色已经褪尽，掌柜将三盏灯笼一一点亮。” | 已确认的当前时段和光照变化 | “想象中的灯笼”“明天点灯”“昨夜点亮”“只是听见别人这样说” |

要求：

1. 先把**参考标注和来源**整理成固定、可复核的结构化语料。明确合成、人工自写、独立复核、获准真实样本的不同级别；若没有第二名独立标注者，只能写“开发自编参考”，不得伪称盲评。
2. 加入含糊指代、跨句指代、引语、否定、传闻、回忆、未来、未知视角及地点变化的**硬负例**，尽可能让错误采纳暴露出来。风险较高时优先放弃显示而不是猜测。
3. 记录每条的输入正文、会话状态前提、期望地点/成员/光照、期望操作或未就绪原因、证据段落与标签来源，不提交私人正文。
4. 与 `zh-visible-clause/1` 做**同批旧版和新版对照**，分别统计 exact、incorrect-accept、abstain、错误放弃（若有可靠参考）、错场景/错人/漏去人及版本漂移。不要把放弃判断当成成功理解；任何零错误率只能针对这批人工样例。
5. 推荐将新方法版本标为 `zh-visible-clause/2` 或等价显式版本。若采用另一种提取边界/本地模型适配器，仍保留上述可审查的输入输出和来源审计；没有获准真实模型就不要新增外部模型调用。
6. 保持仅从可信 completed-history 正文提取；即使玩家 action 内容变化，相同已保存 narrative 在相同前态下应有相同事实判定。

## 四、多事件场景持续性与正确重放

用本地合成的较长故事覆盖至少两个地点、多次复访和一个不确定事件。可在同一独立 PostgreSQL 投影库的多会话测试中组织如下典型路线：

1. 东村酒馆 3 人 V1，普通谈话无变化；两位明确到场后 5 人 V2。
2. 酒馆改称“老周的店”后保留同一 `sceneId`；玩家到西村同名酒馆，两个地点的身份、别名、成员不可串。
3. 返回东村并明确沿用此前场景；人物未再次点名时按受信持续状态保留，不因文字摘要变化就无条件重生图。
4. 某一人明确离场，再有第二人入场；精确更新集合并形成相应视觉版本。反复重读同事件、重发同一 completed-history 页不得重复改变状态。
5. 引入“人员似有变化但无法确定是谁”的不确定叙述；保存未就绪/待核实状态，旧画面不作为当前图展示。
6. 后续文字明确核实当前仍在东村酒馆及完整名单、时间、灯光、观察位置后恢复可显示状态。证明不会无凭据从不确定状态回到旧五人画面。
7. 明确改变灯光/视角后，只在事实确实变化时升级视觉版本，编辑参考必须使用仍合法且匹配的旧图，不能错用初始三人图冒充五人。
8. 再次改名、离开、复访、重启与恢复；同一地点身份、事件对账和当前图关联保持正确。

为避免“事件很多、结果看似通过但其实一直靠硬编码”，至少有一条浏览器/HTTP 路径使用**相同的玩家行动、不同的已保存剧情正文**，提取和画面决策随正文变化；另用多种表达表达同一实际变化，观察行为是否一致或明确保守放弃。

### 重放与版本纪律

YJ-08 将已消费事件、观察和提取方法写入 `yingjie_scene.event` 与 `yingjie_play.extraction`。旧方法版本与新方法版本不能在同一投影流中默默混用。

- 如提取算法或语义发生变化，使用**独立重建的投影库/流**从同一已完成历史重放，核对后再切换消费者；原权威文字回合不改变。
- 记录旧/新方法、来源正文摘要、处理修订、场景差异、视觉版本迁移以及图片是否仍适用。原 `requestKey`/已发送尝试不能因重放任意重命名并触发二次外部付费请求。
- 已记录的图片不因新版提取器放宽解释就自动被评为“审阅通过”；展示/参考/历史归属继续使用 0.1.1 规则与实际授权。
- 注入中断、重复消费、分页、并发重放、同名异地、跨会话和撤权；未知 provider 结果继续 `hold-unknown`，禁止因提取器版本切换重新发旧的可能已送达请求。

## 五、图片选择与 UI 联动验证

使用 YJ-05/06/07/08 已有模块实际验证：

- 同地点同视觉事实：展示仍合格的预设或已审图片，普通交谈不强制新图片。
- 人数或时间变化：先判断已保存视觉状态；没有合格当前图片时保守选择可编辑参考、生成（本地 mock 支持的情形）或 skip。不能将原本待审/损坏/不适用的图片直接展示。
- 含糊离场或未知事实：页面仍可提交文字，图片区明确“当前画面待核实”一类未就绪结果；不显示确定已矛盾的旧图，不自动凭猜测移除人物。
- 关闭生图、刷新、切会话、撤权、下载旧 URL 与异步迟到：原已通过的权限与恢复安全边界不回退。旧图历史归属可保留，但不能抢占新会话或已变视觉版本的当前视图。
- 对于本地 provider 无能力覆盖的四人或未知构图，宁可 skip/no-image，不要假装三张历史原图足以覆盖任意变化。

YJ-09 不以生成更多图片为目标，**本轮真实图片调用保持 0**；避免重复 YJ-02 三张图片实验。新合成语料不足以证明真实图模型长期连续性。
