## 二、完成后应当得到什么

不同开发分项目能够用同一组数据准确回答：

1. 这条画面请求来自谁、哪个会话、哪段已经保存的剧情？
2. 当前是哪一个地点，哪些事实是玩家当前可知、已经发生的？
3. 剧情推进后，画面状态是否真的改变？
4. 本次是复用、生成、参考编辑还是跳过，理由是什么？
5. 请求是否发出、结果是否已知、图片是否保存和审阅？
6. 一张图片能否显示在当前画面，能否进入用户历史，能否作为下一次编辑参考？

完成标志是这些问题具有一致、可校验的表达方式，并通过代表性正反例；不要求本任务做出可玩的映界界面。

## 五、实现方式与最小框架

优先复用九霄固定基线的 TypeScript、Zod 和既有检查工具思路；具体版本从实际 package.json 与锁文件核查，不填“最新版”，不顺带升级依赖。这里是实施建议，不表示映界仓库已经具有同名目录或可运行包。

建议在映界仓库建立一个独立的小型契约包，例如 `packages/contracts`，由一名集成负责人维护。可以包含类型、运行时 schema、纯函数规则、fixtures 和测试；实际目录和公开导出名称由执行者结合仓库确定并记录。不要仅为共享少量类型就搭建完整 monorepo 工具链、发布 npm 包或设计远程微服务。

若需要增加根 package.json、工作区配置或锁文件，仅加入运行本契约包所需内容，集中提交。文档列出的命令必须实际执行后才能标为 PASS。无法安装时，记录真实错误，交付仍可读取的设计和样例；不能把未运行的 schema 或手工检查声称为自动测试通过。

共用契约是各模块交换的数据格式，不自动决定数据库表、部署进程或永久产品架构。结构校验也不能保证模型没有理解错剧情，更不能替代服务端鉴权。

### 6.1 三类来源分别表达

**合成样例**：明确标记 synthetic-fixture，使用 fixtureId 与样例事件标识。不能为了通过生产校验伪造真实用户、会话或存档。它可以带测试归属，但必须与真实来源有清楚区别。

**独立角色卡历史**：映射 YJ-01 已验证的用户、会话、请求/历史记录和修订归属。读取已完成且已经保存的文字；不能把未完成流式片段或失败回合当作最终剧情。该路径没有原生 saveId / branchId 时，应由来源类型表达不适用，不填随机 UUID 或空字符串冒充真实字段。

**原生权威回合**：保留该路径实际具有的存档、分支、回合等信息，区分规则结算与已经可读取的正文。允许先作为明确未接入的扩展类型；不能因结构相似就声称已有运行证据。

服务端应从可信上下文解析归属并验证访问权。客户端送来的 ownerId 或通过 schema 的字符串，不构成权限证明。YJ-03 提供规则接口与负例，真实鉴权执行留给后续接入。

### 6.2 剧情修订与视觉版本分开

用 YJ-02 这条序列证明设计，以下 V1/V2/V3 是本任务候选命名，并非修改原实验记录：

| 剧情阶段 | 当前可见状态 | 视觉版本示例 | 资产/动作 |
| --- | --- | --- | --- |
| S0 首次进入 | 日间，掌柜和两位客人，共 3 人 | V1 | I0 初图 |
| S1 普通交谈 | 人物、空间与光照无实质变化 | 仍是 V1 | 复用 I0，无新调用 |
| S2 两名旅人到场 | 同地点，共 5 人 | V2 | 以 I0 为参考编辑，得到 I1 |
| S3A 无变化复访 | 同地点、同五人状态 | 仍是 V2 | 从已保存资产恢复 I1，无新调用 |
| S3B 傍晚亮灯 | 同五人，时间与光照改变 | V3 | 以已接受 I1 为参考编辑，得到 I2 |

同一个场景可有多个历史视觉版本；同一张资产可被多段无视觉变化的剧情引用。不因每次读取、刷新或普通对话无条件增加视觉版本，也不因人物或场景实质变化却复用原版本。

剧情中“听说另一座山”“回忆昨日”“打算明日离开”不等于当前地点变化。YJ-03 可以使用已标注的事实状态验证规则；它不负责证明 AI 自动分类已经准确。

### 6.3 三个容易混淆的判断必须分开

1. **审阅接受**：图片曾经在明确来源与目标状态下被接受，有记录可追溯。
2. **当前可显示/可复用**：归属、当前地点、目标可见事实、资源状态以及当前显示许可相符。历史中合格的三人图不能当作当前五人画面继续显示。
3. **可作为编辑参考**：参考资产归属正确、已获相应接受、内容可读且摘要匹配，保留的空间/人物特征适合目标，变化可以明确描述。它允许来自较早的视觉版本，例如 I0 → I1。

不要把“参考图视觉版本必须等于目标视觉版本”写成硬规则，否则会阻断正常增人编辑。也不要只检查文件存在就允许任何图片成为参考；错误会话、错误地点、未审阅、已拒绝或摘要不匹配的图片都需有明确拒绝理由。预设资产若需要跨会话复用，须以独立资产来源和获准访问范围表达，不以私人历史图片的跨会话通行规则替代。

审阅拒绝不抹除尝试记录。当前不可显示的资产也不能自动算作永久删除；用户历史展示、审计留存和实际文件清理属于不同用途，具体删除产品深度仍后置。

## 七、请求、关闭与迟到结果

### 7.1 最少需要区分的状态事实

状态名称可以精简，但必须区分：尚未发出、已发出并等待、收到图片、确定失败/拒绝、结果未知，以及本地停止等待。图片收到以后还需要资产保存状态和审阅状态，不能用一个 success 同时表示所有步骤。

每次新尝试都有独立标识，并关联同一个逻辑决策或请求；来源事件的重复投递不应无条件变成新的付费尝试。规范化输入、参考内容与目标状态怎样参与去重，应给出清楚规则和例子；YJ-03 只验证规则，不声称已实现跨进程 exactly-once。

本地超时只能证明等待结束。若请求已可能到达供应商，应保持 outcome_unknown 或等价语义；只有具有真实能力和标识时才允许查询原请求。查询未知或不支持，且没有已验证的回调或其他结果核对方式时，保留待处理状态和原因，不自动假定失败并重新调用。其他恢复方式在实际供应商能力明确后验证。

明确拒绝、已确认失败、请求根本未发出、结果未知需要不同处理依据。重试上限、具体退避和预算产品规则本轮不冻结；规范必须能够表达“这一次是否允许再试及为什么”。

### 7.2 关闭生图不等于远端取消

区分至少三件事：停止安排后续生成、本地停止等待/当前呈现失效、供应商确认取消。前两者不能伪造第三者，也不能据此断言不收费或不会迟到返回。

关闭后到达的图片不得自动抢占当前画面。已返回结果如何按原来源保留、是否进入普通图片历史，应独立判断；不要借这个任务冻结生图关闭开关是否隐藏已显示旧图等未确认界面细节。

YJ-02 recorder 中的 cancelled 仅是离线分类示例，不能直接解释为远端取消已得到证明。未来若供应商提供取消能力，还要按其实际语义填写。

### 7.3 迟到结果以当前适用性为准

如果剧情从第 1 轮推进到第 2 轮，但视觉状态仍是 V1，则第 1 轮返回的合格 I0 可能仍适用。不能仅用“不是最新剧情修订”拒绝所有图片。

若当前已变成 V2、另一地点、另一会话，或展示目标已失效，则 V1 的迟到结果不能覆盖当前画面。它只能在原归属仍有效且符合保留规则时关联原历史。会话删除、权限撤销、图片失效或本地关闭后，也不能因为稍后收到成功结果就重新激活当前视窗。

本轮用纯函数与离线事件序列证明以上决策；实际并发、原子更新和重启恢复留给 YJ-05 / YJ-08 / YJ-12。

### 步骤 C：用已存在证据准备样例

新增契约 fixtures 与索引，引用 YJ-02 的 I0/I1/I2，不复制或改写原图与历史调用记录。样例说明所用字段哪些来自真实记录、哪些是本次新增的离线示意值。

YJ-01 的真实本地会话与 YJ-02 的合成酒馆从未联通；二者只用于分别验证来源映射和画面状态，不能拼成一条伪造的端到端调用证据。

### 步骤 D：执行有意义的离线检查

检查真实跨字段关系与拒绝原因，不为每个简单 getter 或与实现逐字相同的逻辑写形式测试。至少覆盖第十节的关键边界，按风险合并用例即可，无需机械凑数量。

### 步骤 E：只读审阅并收口

可以并行审阅来源映射、状态规则和负例覆盖；公共类型、根依赖与锁文件仍由一位负责人汇总修改。没有必要为每类数据创建独立服务或开发仓库。

完成后提供：

- 契约文档、可导入的最小契约包及公开导出说明。
- 正例/负例 fixtures、YJ-02 证据引用索引和实际检查命令。
- `docs/reports/YJ-03-shared-contracts-report.md`，区分已通过、失败、未运行和依赖未满足。
- 契约版本、未决字段/能力清单、后续分项目消费说明。
- 更新 README、任务看板、验证与交接；记录实际提交。

## 十、必须覆盖的离线边界

| 编号 | 输入或事件序列 | 期望与要防止的错误 |
| --- | --- | --- |
| C01 | 角色卡已完成历史具有真实归属、请求和修订，无原生存档/分支字段 | 可以表示；不要求伪造 saveId / branchId。未完成历史不能冒充最终剧情 |
| C02 | 合成 fixture 或原生回合被错误标记成真实角色卡来源 | 明确不匹配；不能把两类试验拼成真实联调 |
| C03 | S0 → S1 普通交谈，剧情修订变化而视觉事实不变 | V1 / I0 可复用；无新图片尝试 |
| C04 | S1 → S2 新增两人 | 创建目标 V2；I0 不可直接当当前五人图，但可以在条件满足时作编辑参考 |
| C05 | S3A 复访与 S3B 傍晚；对照错误地以 I0 替换计划要求的 I1 | 复访恢复 I1；灯光变化产生 V3，并以 I1 为参考，来源链可追溯。不能仅凭 I0 曾被接受就丢失应继承的五人状态 |
| C06 | 错会话、错用户归属、错场景或非法原生分支关联 | 拒绝显示/参考并保留原因；schema 通过不等于服务端已授权 |
| C07 | 未审阅、人数无法判断、已拒绝、已失效、文件缺失或摘要不匹配的资产 | 不能自动显示或成为合格参考；不只检查 assetId 存在，也不把无法判断当作审阅通过 |
| C08 | 旧剧情修订的结果迟到，但当前视觉状态仍匹配；对照当前已改变的情况 | 前者在其余条件满足时可用；后者不能覆盖当前画面，不能只比较最新回合号 |
| C09 | 请求发出后超时、关闭、离开会话，再收到结果 | 本地停止与远端取消分开；迟到结果不能抢占失效的显示目标；未知结果不自动新调用 |
| C10 | 同一来源事件重复交付、同一结果重复回传 | 保持逻辑身份并识别重复；不无条件建立第二次请求或重复历史记录 |
| C11 | 查询能力 unknown / unsupported，providerRequestId、费用和模型为空 | 合法表达未知并阻止依赖未证明能力的动作；不填假 ID 或 0 费用 |
| C12 | 图片偶然多出道具、文本是回忆/计划/传闻，或包含玩家未知信息 | 不据此更新当前权威事实/地点；标注这是规则样例而非自动语义识别通过 |

关键负例应有最小合法对照，尤其是旧剧情修订但视觉仍适用的情况，避免只证明“所有结果都拒绝”而阻断正常流程。还应验证最终选定的 schemaVersion 与必填字段约束。对真实 API 故障、数据库事务与生产权限，明确记 NOT_RUN，不以离线负例冒充实测。

## 十一、可以并行与必须等待的工作

YJ-03 内部可以并行做只读来源核查、样例整理和契约审阅。最终导出格式、公共类型、根配置与检查入口由同一集成负责人维护。

契约通过本任务的工程检查并形成固定版本后，后续任务按各自任务书推进：

| 分项目 | 从 YJ-03 接收什么 | 仍然需要的条件 |
| --- | --- | --- |
| YJ-04 场景身份与变化 | 来源类型、地点、视觉状态、决策与样例 | 真实来源读取和持久化实现 |
| YJ-05 图片任务 | 请求/尝试、能力、参考、资产、审阅和错误约定 | 真实后端供应商入口及认证；查询/取消/计费按实际能力补齐 |
| YJ-06 界面 | 可显示状态、等待/失败/未知、资产和历史样例 | 可以先用明确标记的样例；真实数据接入另行验证 |
| YJ-07 资料匹配 | 地点标识、资产来源、适用条件和无匹配结果 | 现有获准资料；不要求大量新素材生产 |

本任务书本身不表示这些分项目已经开工或已向外部开发者派发任务。YJ-05 的模拟适配器可以用于开发，但真实供应商关口不能由模拟结果关闭。没有已验证的查询、回调或其他结果核对机制时，不能声称已具备未知结果自动恢复。

## 十二、完成检查与真实状态

只有满足以下条件，才能将 YJ-03 标为已完成：

1. 类型、schema、数据字典与 fixtures 相互一致，有唯一维护位置和版本。
2. 已核查独立角色卡来源的真实字段，保留原生路径与 fixture 的区别。
3. 已执行并记录 S0 → S1 → S2 → S3A → S3B 的离线契约检查，引用原证据而不修改它。
4. 关键归属、参考、未知结果、迟到、重复和视觉适用性反例具有明确检查结果。
5. 后续分项目可以导入或明确消费契约，检查命令可以复跑。
6. 供应商缺口、未执行项和后置产品问题仍清楚可见。
7. 实际变更、依赖、验证和交接已经提交到任务分支，并核对远端 HEAD。

完成 schema 不能汇报成已完成映界后端，离线状态测试不能汇报成已完成真实恢复，文档审阅不能汇报成正式产品验收。遇到阻塞时，完成可完成部分并给出具体状态，不把整个项目笼统标为停工。
