## 三、工作包 A：反馈回执丢失后的幂等恢复（优先）

**已确认的实现边界：** YJ-11 的 `ImageHistory.report` 在事务内先调用 `target(...)` 重新核验原件，再查询 `yingjie_history.report` 中相同 `scope + command` 是否已提交；React 的反馈 `command` 放在组件 `useRef`，重新加载标签页后该内存值会丢失。第一次 POST 可能已提交但回执在网络中丢失，随后图片撤权/审阅撤下或页面刷新，重复发起可能无法核对原命令结果。

实现并验证**明确、安全、最小范围的恢复机制**：

1. 一条反馈对应稳定、受信的 `command UUID`。在发送前保留相同请求的身份和必要参数摘要；断网、页面刷新、丢回执后对相同反馈沿用原 UUID。不依赖“浏览器重试时重新生成一个 UUID”。
2. 可在当前账户/当前会话仍有访问权时，先以 `scope+command` 查询**已持久提交的回执**，确认原参数与原记录一致后，返回原反馈 ID 或最小状态。目标图片后来被撤权/无权下载不代表已经提交的反馈从未存在。但已登出、账号切换、会话删除或已失去会话权限时仍必须拒绝；不能通过 command 枚举其他人的反馈。
3. 明确区分：A) 服务端还没接收，B) 服务端已写账但响应丢失，C) 已提交后图片撤下，D) 反馈参数改动但重用 UUID，E) 账号/会话切换。A 可使用原命令在验证后受控提交；B、C 只核对已提交回执；D 返回冲突；E 拒绝并清除旧视图。未知结果不能自动宣称成功或失败。
4. 客户端只将**非敏感的待确认指令最小信息**保存到与账户/会话绑定的当前标签会话状态，或由受信服务端提供带权限的回执查询。不得保存 Cookie、完整私人反馈或原图字节；同意把有敏感风险的说明留在受信服务端。页面恢复时先核对，而非自动无限重发。
5. 用户更改类别、文字说明或目标图片时，必须作为新反馈命令；不得把新内容附在旧 UUID 上“重试”。多标签页、两进程和 UUID 大小写变体须继续保持幂等。
6. 断网回执恢复不能意外触发 YJ-05 图片任务；浏览、反馈、刷新和状态查询期间的新增图片发送次数必须为 0。

先写一个能重现“**POST 实际成功，但回包被拦截，接着原图被撤权**”的定向测试。再定向修补服务端的回执核对顺序和前端可恢复状态，随后在真实 PostgreSQL + HTTP + Chrome 验证。不要在未经当前会话鉴权的情况下返回任何旧回执。

## 四、工作包 B：网络、浏览器与视图生命周期

至少用可重复的网络故障注入覆盖：

| 情境 | 必须满足 |
| --- | --- |
| POST 反馈发送前断网 | 未产生审阅反馈或能安全核对后提交；页面准确显示未确认 |
| 反馈已成功提交、响应丢失 | 刷新、恢复网络后查到原反馈 ID，新增记录 0；同 UUID 仍唯一 |
| 反馈提交后图片撤权 | 当前图与历史原件已不可读；在同一已授权会话仍可核对**原反馈提交**，不凭历史反馈重新授予素材访问 |
| 旧 GET 历史分页/详情延迟 | 切换会话或账户后，旧数据不覆盖新会话；AbortController 之外仍验证归属、修订和响应序号 |
| 登出、Cookie 过期、切换账号 | 私有历史/原件下载不再有效，页面不显示旧缩略图；网络恢复不自动加载旧账户内容 |
| 浏览器后台休眠再激活 | 重新获取当前身份、会话、修订、媒体资格和开关状态，不能凭过期内存继续显示已撤权图 |
| 两标签页同时控制同一会话 | 同一反馈命令不重复，图片生成开关序号不被旧标签覆盖；其他会话、其他账户之间无串图 |
| 反馈页面刷新或快速反复开关面板 | 待确认状态可恢复或被安全核对，页面不冒充“已审核”；文字输入仍可用 |
| 当前图片返回后会话已经切换 | 原件进入原 attempt/历史，当前页不显示错误 scope 的图片 |
| 浏览器历史回退、缩放和窄屏 | 图片 contain 不失真；键盘、触控模拟、滚动、反馈按钮、加载/错误提示可操作 |

必须验证视图的**账户 + 会话 + 修订 + 许可序号**，不能只依赖终止旧 fetch。图片下载路由依然要重新验证授权、审阅与实时文件摘要。已传到浏览器的旧像素无法远程收回，不要作虚假隐私保证；可验证后续请求被拒绝及应用当前界面被清空。

## 五、工作包 C：任务 unknown、并发和进程恢复

## 六、工作包 D：PostgreSQL 与原件目录的一致性备份/恢复

现有 Node + PostgreSQL 与私有图片文件目录之间**不存在跨资源原子事务**。YJ-11 报告提示备份恢复必须一起保留数据库、原件和世界书版本。YJ-12 用**完全合成的测试数据库/素材**完成可重复的恢复演练，严禁备份私人账号数据库到仓库。

最小演练：

1. 创建独立测试 PG 与私有原件目录，生成受信普通卡会话、历史/场景/世界授权、图片任务、尝试、asset、反馈、decision、review_event（含被撤下资产与共享摘要文件）。
2. 在明确停写/停止任务派发的点取得一致性逻辑快照：按已有工具执行本地 `pg_dump` 或等效受控导出，同时保存原件目录清单、SHA-256、格式/尺寸、复数引用计数或共享键清单、必要版本号。**不读写真实凭据**。如果尝试热备份，必须单列无法确保的跨资源原子窗口。
3. 在全新隔离库和私有目录恢复，逐项验证原修订、稳定地点与 visualVersion、world binding、task/requestKey/attempt、unknown、选择、审阅纠错 append-only 顺序及 bytes SHA-256。
4. 故意损坏/删除一份原件、缺一份世界书授权或缺审阅事件时，恢复前/启用前的**一致性审计应明确报错，当前图片与编辑参考不可显示/派发**；不要用库里旧的 accepted 自动跳过实时文件验证。
5. 验证同一 SHA 的多个资产/多个修订都能恢复独立归属；不按单个 asset 随意删除共享原件。
6. 加入“PG 成功、文件未恢复”和“文件恢复、PG 未成功”的隔离测试。应用必须保持安全停用或无法展示，而不是自动创造缺失的任务/图片。
7. 恢复完再启动只读视图，显式批准恢复派发前复核所有已发送 unknown；不要用完整恢复流程自动补发远端任务。
8. 交付可执行的**合成备份演练脚本与恢复核查/回退说明**。生产级在线备份、跨主机对象存储、灾备 RPO/RTO、正式数据清理策略未验证时列 NOT_RUN，不虚称已经有生产灾备能力。

如环境不能运行 `pg_dump`，可先验证已有测试 PG 的快照和原件审计，并将真正数据库导出/恢复标为 NOT_RUN；不能用两个 JSON 文件代表已完成完整 PG 恢复。
